# Broker OS Implementation Plan

> For agentic workers: implement independent modules with explicit file ownership, test each boundary, and review the complete integrated system before completion.

**Goal:** Deliver the Phase 3 Broker OS acceptance workflows while preserving the Phase 1/2 native simulated terminal.

**Architecture:** Extend the serialized domain snapshot with broker configuration; use pure policy resolution, centralized capabilities, additive PostgreSQL mirrors, separate administrative APIs, and a separate operations frontend.

**Tech stack:** Existing Go, shopspring/decimal, pgx/PostgreSQL, Next.js 16, React 19, TypeScript, React Query, Vitest, and Playwright.

**Spec:** [Broker OS design](../specs/2026-10-02-broker-os-design.md) and the supplied Phase 3 request.

## Global constraints

Financial values remain exact decimal strings. Keep existing owner authorization and account risk validation. All engine mutations commit ledger/audit/state before publication. Never wipe old data, edit fills, add external execution, or expose inactive menu destinations. Keep current marketing design and trader workflows.

## Review focus

- Different groups receiving the same quote must see their own executable spread and preview, including after a pricing update.
- Partial close fees and forced closes must use saved opening economic terms and never duplicate ledger charges.
- Restart and concurrent rollover/stop-out processing must not duplicate swaps or liquidations.
- SUPPORT/TRADER and foreign tenant requests must fail at all admin command and report boundaries.
- Loading an old snapshot and applying migration 004 must preserve Phase 1/2 data and initialize absent configuration safely.
