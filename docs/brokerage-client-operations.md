# Brokerage client operations UI

`src/client/pages/ClientOperations.tsx` exports `ClientOperations`, `ClientTagsAssignments`, `ClientNotes`, and `ClientTasks`. Each accepts `{ api: string; client: Row; onChanged?: () => void }`. `api` is the existing admin path `/instances/:instanceId/brokerage`; the shared request helper supplies `/api/v1`, same-origin credentials and CSRF protection. Use the focused exports in the client profile, notes and tasks tabs, or compose them through `ClientOperations` in an operations tab. `onChanged` refreshes the surrounding profile and activity view after a successful mutation.

All reads and action controls use workspace permissions. Notes and task reads need their dedicated read permissions. Mutations need their corresponding write permissions. Staff choices use the Core directory only with `staff.read`; choices are active, server-scoped memberships, deduplicated by identity. Assignment and task owner values are user IDs, never membership IDs. The directory returns at most 100 memberships per search; searching by name or email permits selecting beyond the initial page. The server remains authoritative for active identity, environment and instance validation.

Client tags display current assignments including archived tags. Assignment choices exclude archived and already assigned tags. Removing a tag removes only its client association. Staff ownership supports account manager, compliance reviewer and support owner, including removal by sending `staff_id: null`. Without staff directory permission, existing assignments remain visible and permitted removal remains available; the UI does not request manual identity IDs.

Internal notes support creation, editing, pinning, unpinning, deletion, staff/private visibility and preserved history. Edit, pin and delete actions are limited to the author or a staff administrator, in addition to `brokerage.notes.write`. The server applies the same policy. Deleting shows the concrete note excerpt and explains preserved history. The history dialog consumes the admin-only, paginated `GET /clients/:id/notes/history?limit=25&offset=...` response (`Page`) and displays immutable revisions including deleted notes. History entries use safe editor names and revision timestamps; private notes must be filtered by the backend before returning history.

Client tasks list persisted client-scoped tasks with status filtering and 25-row pagination. Each row shows owner, priority, due date, created date, optional details and an explicit overdue label. Staff can create, edit, clear due dates or owners, change status, and mark a task complete. Date/time fields use the browser's local timezone and send ISO timestamps. Editing a task preserves its existing owner when staff directory access is unavailable. An unchanged owner is omitted from task updates, so changing another field does not reassign ownership.

Every mutation sends a generated `Idempotency-Key` through the existing CSRF-aware request helper. An unchanged failed request retains its key on retry. Form bodies contain only fields accepted by the strict backend schemas, with client-side length, enum, selected-option and date validation. Failed writes preserve form input and expose the server's error message. Lists provide loading, error/retry and empty states.

The components reuse the existing panel, form, dialog, badge, notice and record styles. The containing stylesheet should add `client-operation-actions` as a wrapping button row, `client-note-pinned` and `client-task-overdue` as small inline status labels, and enforce 44px touch targets inside `.client-operations`. No sample client data, identities or tasks are injected.

## Advanced client filters

`ClientFilters.tsx` exports `ClientFilters({ api })` and `clientFilterKeys`. Render the filter component on the admin client list and pass `clientFilterKeys` into `ResourceView`'s `filterKeys` prop. The advanced filter form applies country, verification status, client type, acquisition source, tag, account manager and registration dates together. It preserves the common search/status parameters, resets pagination to zero on Apply/Clear, and keeps filters in the URL for navigation and sharing.

Country codes are normalized to uppercase and validated before the URL changes. Source length and enum choices follow the strict client-list schema. Registration dates become ISO timestamps at the start/end of the selected local calendar day; the end date includes that entire day. Reversed ranges are rejected without issuing an API query. Tag choices are workspace-scoped, and archived tags remain available for filtering existing historical associations. Staff filtering uses active scoped memberships and name/email search only when `staff.read` is permitted. Invalid partial form input remains local until Apply. The advanced summary and its form need the same 44px touch target styling as client operations.
