# Disaster recovery

Operational targets are configurable: initially approve RPO 24 hours for daily logical backups and RTO four hours. Managed continuous WAL/PITR may target five-minute RPO after verified drills. These are planning targets, not guarantees or conclusions from a small local fixture.

Schedule a separate daily 02:00 UTC backup job in the operator's scheduler. Suggested retention: 14 daily, eight weekly, 12 monthly encrypted archives in independently controlled offsite storage with KMS, versioning/object retention and least-privilege backup/restore roles. Alert on missing/failed jobs; run regular restore drills. No external scheduler/storage/KMS/PITR has been configured here.

`npm run db:backup -- <unique-file.azbk>` streams custom pg_dump through AES-256-GCM. Configure BACKUP_DATABASE_URL (reviewed backup role that can read all required tenants), separate base64 32-byte BACKUP_ENCRYPTION_KEY, DB_TLS_CA_FILE and PG_BIN. Credentials use child environment, never URL arguments. Version/nonce header is authenticated; exclusive creation prevents overwrite. Failed partial archives must not be retained. Apply OS ACLs/disk encryption, especially on Windows where POSIX mode is insufficient. Record application/PG/tool versions, migration checksums and key version beside each object. Cluster roles are not in a database dump; provision reviewed roles before restore. Back up vault/backup keys separately.

Create a separate empty destination and configure RESTORE_DATABASE_URL. `npm run db:restore -- <file.azbk>` authenticates the entire archive into a protected temporary dump before touching the database, rejects a nonempty target, then runs pg_restore with exit-on-error and one transaction. Temporary plaintext is removed after completion/failure. Match PG major/tool versions and checksum compatibility; do not run older code against a newer schema.

Before traffic: verify checksum ledger, runtime privileges/FORCE RLS, tenant counts/references, immutable audits, key decryption and two-tenant portal/auth smoke tests. Keep outbound workers stopped during validation to prevent replay of historical effects. Receiver/provider deduplication remains necessary after restore. For tenant recovery, restore the full database/PITR point into isolation first; extract by every ownership key and reconcile shared identities/catalog/audit deliberately. No live tenant recovery tool is included.

Configure managed PITR or encrypted WAL archiving independently: logical backups do not provide PITR. The actual isolated local PostgreSQL 16 TLS dump/restore checked migrations, tenant data and restricted RLS; evidence is in ignored artifacts/pg-acceptance. Encrypted utility acceptance is recorded separately when run. Offsite retention, KMS permissions, production-scale RTO and PITR remain deployment gates.
