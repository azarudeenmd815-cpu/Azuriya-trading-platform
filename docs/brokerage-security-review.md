# Brokerage CRM implementation security review

This document records the internal implementation review of the Brokerage CRM added to Azuriya Core. It covers the new HTTP routes, domain services, database policies and worker integration. It is engineering verification using the local PostgreSQL-compatible PGlite test runtime, not an external independent audit or a production certification.

## Changes resulting from review

| Finding | Effect | Correction and evidence |
| --- | --- | --- |
| Brokerage business events originally placed their tenant fields at the top level, while the existing webhook worker reads `payload.scope`. | Configured product-instance webhooks missed Brokerage events. | Brokerage events now use the normalized scope envelope. A persisted-event test verifies delivery to its matching instance and one delivery per endpoint/event. |
| The internal `brokerage.email` event was missing the email-specific fanout and missing-handler guards. | A future scope-bearing email envelope could enter webhook fanout; a worker without its email handler could falsely complete the job. | Email envelopes are excluded from webhook fanout, and missing email handlers fail the job through the existing retry mechanism. Dedicated tests cover both boundaries. |
| Approved profiles could change `full_name` while preserving approved KYC and active lifecycle state. Automatic re-review events also omitted their previous KYC/lifecycle state. | Verified identity information could change without re-review, or re-review state changes could lack clear audit evidence. | Staff and client profile edits now treat full name as an eligibility field, alongside residence, country, birth date and client type. The HTTP regression observed active/approved before the fix and now requires onboarding/required/in-progress. Events include safe previous/resulting KYC and lifecycle states without the identity text. Existing restricted, suspended, rejected or closed states remain protected. |
| Notes had persisted revisions but lacked authorized history endpoints and author/editor display names. | Staff could not inspect revision history through the application. A naive history implementation could expose earlier private text after sharing the current note. | Added per-note and client-wide paginated history routes. Both current note visibility and historical revision visibility are checked. The tests cover original private text, deletion, cross-client identifiers, tenant scope and permission denial. |
| Deposit retry transitions can revisit `processing`, but the original transaction observation constraint permitted one row per request/status. | `processing → requires_action → processing` failed with `23505` instead of recording a valid workflow retry. | Forward migration `015_brokerage_workflow_observations.sql` removes the request/status uniqueness constraint. Locked request rows and transactional idempotency still prevent request replay; the passing regression verifies separate immutable observations for every allowed transition. Applied migrations 001–012 remain unchanged. |

Client notifications use explicitly scoped ownership. Partner and payout events resolve their client through their tenant-scoped partner record, and payment review events identify their client. Internal note, task, assignment, risk and tag events do not generate client messages. Email content is encrypted in the outbox and checked against the recipient's active membership and tenant/product hierarchy before delivery.

## Verified boundaries

- Staff routes reuse active tenant membership, role permissions and the complete organization/brand/environment/product-instance hierarchy. A credential for one product instance cannot select another instance.
- Client routes require a separate interactive customer session with active membership. They derive the client from authenticated identity; submitted client identifiers and foreign account/document identifiers do not override it.
- Tenant-approved Core support can read the authorized Brokerage records. Brokerage writes are denied, and sensitive destination access is denied even with an enrolled, verified support session.
- High-risk actions require an interactive business session, a correct current password, enrolled MFA, and a session verification within 15 minutes. These checks precede the idempotency lookup, so a replay cannot bypass a wrong password or expired MFA window. API/service credentials are denied those interactive approvals.
- Every new Brokerage table has enabled and forced RLS. Queries with organization alone, or a mismatched brand, environment or product instance, return no Brokerage rows. Composite foreign keys protect account/client, KYC case/document, payment method/request, referral/partner and payout/accrual ownership.
- Withdrawal and partner-payout destinations are encrypted with authenticated request, client, purpose and all four tenant fields. Finance tests verify envelope copying fails authentication and that API responses, immutable observations, audit metadata and replay records do not contain full payout destinations.
- Monetary requests use decimal strings and PostgreSQL numeric values. Workflow observations, referrals and commission accruals are protected against update and delete; payout allocations retain their release history. Actual accounting and provider trading balances are separate from these operational observations.
- Account activation requires an externally confirmed identifier and evidence reference. Unsupported connectors retain pending/unavailable states and do not fabricate account execution, payment settlement or balance movement.
- Templates accept only named variables from an explicit allowlist. Expressions, property access, prototype variables and malformed braces are rejected. They are delivered as plain text; the provider abstraction receives the same outbox event ID as its idempotency key. Local tests verify encryption, recipient gating and template tenant isolation; they do not claim real provider delivery.
- Notes, tags, consent document text, filenames and email-template previews are rendered as text in React. No new CSV export is implemented, so no export-specific formula execution surface was added in this phase.

## Test evidence

`tests/brokerage-boundaries.test.ts` contains focused HTTP and persisted worker/database checks for the review findings. The existing Brokerage client, account and finance test files cover domain lifecycle, ownership, credential vault, immutable finance, exact decimals, idempotent creation and direct RLS adversarial cases.

The targeted run of `brokerage-boundaries.test.ts`, `brokerage-clients.test.ts` and `brokerage-finance.test.ts` passed **52 tests across 3 files**. The boundary review contributes **16 tests**. Targeted lint verification passed for the boundary tests and the changed client service/routes.

The note-history tests were first run against the missing endpoints and absent names, and failed. The full-name HTTP regression was run before its fix and returned active/approved. The deposit retry regression was run before its database correction and raised the original request/status unique-constraint error. These reproductions establish the behavior corrected by the implementation.

The later [final verification report](brokerage-verification.md) records **190 passing tests across 16 files**, browser workflows, measured response times and responsive viewport results. The targeted numbers above describe the earlier review run, not the final suite.

The final follow-up also reproduced a real PostgreSQL calendar-date defect in `Asia/Kolkata`: SQL `DATE` values serialized through local-midnight JavaScript dates could move to the preceding UTC day. Client list/detail, profile and onboarding projections now return the calendar date as text, and eligibility checks compare calendar dates. An unchanged approved profile therefore retains its verified identity and state. The real-driver regression and read-only PostgreSQL/browser confirmation are recorded in the final report. Staff client-consent evidence is now available through a permission-gated, fully scoped, paginated endpoint that preserves historical document versions without exposing request IP/user-agent data.

## Remaining operational dependencies

Private KYC object storage is intentionally unavailable until an encrypted storage implementation and validated upload/access receipts are configured. Document registration stores metadata with an awaiting-upload state, not uploaded contents or public links. Email delivery requires the configured provider and sender; local verification uses a provider test implementation. Live trading/payment connectors, remote provider settlement and reconciliation remain outside this phase. Worker delivery is durable and retryable; external duplicate prevention depends on the provider honoring the stable event idempotency key.
