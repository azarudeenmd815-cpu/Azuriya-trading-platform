# MFA and invitation lifecycle

Core TOTP is mandatory in staging/production. Tenant admins can require MFA for all staff, roles or individual owners. Effective policy combines active staff memberships and identity/Core requirements. Required unenrolled identities receive a limited challenge after password verification, without protected access. Existing sessions lacking MFA are invalidated on their next request. Enrolled identities always challenge on login.

RFC 6238 SHA-1 TOTP uses six digits, 30-second counters and one adjacent counter each side. Locked counters prevent replay. Setup returns secret/QR only during enrollment. Global identity seeds use the existing AES-256-GCM credential encryption primitive with authenticated user binding in Core-only RLS rows; they do not belong to an arbitrary tenant vault. Hash-only host-bound challenges expire in five minutes with eight permitted failures and shared route limits. Ten recovery codes appear once, remain hashed, and are consumed transactionally. Regeneration/optional disablement requires password plus code and invalidates sessions. Mandatory MFA cannot be disabled. No administrative bypass endpoint is provided.

Invitations bind canonical scope, staff/client kind, approved role, issuer, hash-only token and expiry. Links carry tokens in fragments. The branded email job is encrypted and requires an active matching portal domain in protected environments. Acceptance validates tenant/portal, expiry, revocation, single use, issuer authority and role scope. Existing identities prove their current password; disabled/Core identities are rejected. An email advisory lock serializes concurrent identity creation. Approved acceptance activates the exact membership and audits it. Acceptance returns no session; sign-in completes MFA. Rotation/revocation suppress stale unsent email jobs. Integration tests exercise identity/recovery; real external delivery is a staging requirement.
